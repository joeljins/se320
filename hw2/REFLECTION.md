1. I think closed-box testing is easier for me at this time. It was easier to write out a case for each equivalence partition. I like the concept of property-based testing, but my lack of familiarity with the testing library holds me back, and my generators were the hardest part to get right. With more experience, I think I would start to prefer property-based tests, because generators try many more inputs from each partition than my hand-picked examples, so they are less likely to miss a case. I had trouble working out which assertions stay true on any input, such as checking `arr[result].equals(elem)` instead of an exact index when duplicates exist. The downside of closed-box testing is that I only test the inputs I think of, so a boundary or duplicate pattern I didn't consider goes untested. Property-based tests try many more inputs per partition, including edge cases I wouldn't have picked.

2. If I only had the tests, I think property-based tests would be more useful. A property like "the returned index holds the element" states the general rule directly, while concrete tests make me infer the rule from examples. The generators also show what inputs are considered valid (for example, sorted arrays of integers). Concrete tests would still be useful for single-input cases like the null and empty array messages, and for specific cases like checking that both middle elements of an even-sized array can be found.

3. I think property-based tests would be easier to update. The properties describe general rules, so many would remain valid when the spec changes, with small tweaks if necessary. For example, if the array became sorted in decreasing order, I would change the generator to sort descending, and the properties would work as they are. With closed-box tests, the arrays would have to be rewritten by hand and each expected index rechecked. If the function instead took a set of elements and returned a boolean, the return type would change, so most properties would need rewriting, and the closed-box tests would too. The invalid-input tests (null and empty) would survive in either style. Overall, the cost of changing a property-based suite is mainly in the generators, while for closed-box tests it is spread across every individual test.
